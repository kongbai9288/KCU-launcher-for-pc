## 先说清楚这两条从哪来

F028-03 是「把服务器日志与控制台 stdout 里出现的**命令文字**作为触发条件，命中后执行预设动作」。

013 轮你答复过两条相近但不相同的口径：

| 编号 | 原文答复 | 原本问的是 |

问题就在这：Q-D02 那条是「AI 容器调用启动器能力」时的授权，F028-03 是**服务器日志驱动的自动化**，不是 AI 请求。两者要不要同一套口径，之前没定，我当时只写了个问号。下面把它拆成具体画面。

还有一个容易忽略的事实：日志里的 `issued server command: /op Notch` 是**玩家输入的文字**，不是服务器真的执行了 `/op`。它是文本，不是授权。所以「服务器出现的命令文字」这个触发源，天然带着「输入不可信」的属性 —— 这是两条问题的共同背景。

## Q-028-01：命中后是否每次都要手动同意

### 场景 A｜凌晨三点，服主睡了

日志刷出 `Can't keep up! Running 2345ms behind`，规则「卡顿预警」命中，预设动作是 `save-all` 然后广播「服务器将在 30 秒后重启」。

- 若每次手动同意：弹窗在没人看的屏幕上挂着，超时后不执行 → 服务器一路卡到崩，自动化等于没做。
- 若不弹：`save-all` 会写盘。可这台服务器可能已经处于半损坏状态，此刻写盘正好把坏档固化 —— 这就是你之前说的「我只是怕用户把自己的存档用坏了」。

**这条场景里，「安全」和「有效」是反的。**

### 场景 B｜玩家在公屏打字诱导

玩家在聊天里发 `/op Steve`（没权限，就是文字）。服务端记一行 `issued server command: /op Steve`。如果规则的触发文字里含 `/op`，且来源限定没勾「仅服务端输出」，**这行会被命中**。

- 若预设动作是「记录并通知服主」，不弹确认也无害。
- 若预设动作是「封禁发这条命令的玩家」，且不弹确认 → 玩家可以拿聊天文字当遥控器，让启动器替自己执行动作。

所以 Q-028-01 不是孤立选项，它和 Q-028-02 绑在一起：**越不弹确认，动作白名单就越得收紧**。

### 场景 C｜模组刷屏

某个模组每秒打一行含关键字的日志，一条宽泛规则一秒命中 60 次。

- 若每次弹确认：UI 瞬间被 60 个弹窗打爆（虽然按你的规矩每个都能关、流程后 0 残留，但手感极差）。
- 若有冷却 + 不弹：只执行一次，诊断行记「已合并 59 次」。

F028-03 里已经写了冷却去重，但冷却只对「不弹确认」有意义。

### 场景 D｜用户刚写完规则点「测试」

贴一段日志样文，看会命中哪条、将执行什么动作。这个入口**不该弹「是否同意执行」**，也不该真发命令 —— 它只要预览。F028-03 已经这么设计了，提出这一点是要说明「手动同意」不能一刀切套到所有入口。

### 可选口径

| 编号 | 口径 | 场景 A | 场景 B | 场景 C |
| --- | --- | --- | --- | --- |
| Q1-A | 规则级一次性授权：新建/编辑规则时弹一次「这条规则以后可以自动执行吗」，之后不再弹 | 有效 | 风险集中在新规则那一眼 | 有效 |
| Q1-B | 按动作分级：只读动作（诊断行、通知、审计）自动；会写存档 / 发服务器命令 / 动文件的动作每次弹 | 只读部分有效，写盘动作夜里不执行 | 诱导也最多只能触发只读动作 | 有效 |
| Q1-C | 完全复用 013 的「每次请求」 | 失效 | 最安全 | 会被刷屏 |

**我倾向 Q1-B**，理由是你明确说过怕把存档用坏，而「写盘 / 发命令」正好是那一类；只读动作全自动不会碰存档。但这只是倾向，没写进功能 md。

## Q-028-02：预设动作允许哪些命令

### 先按「会碰到什么」把动作分五类

| 类 | 例子 | 会碰到什么 |
| --- | --- | --- |
| C1 只读 | 写 `[KCU]` 诊断行、桌面通知、追加审计记录、日志页高亮 | 不改存档、不碰服务器、不外传 |
| C2 游戏内广播 | `/say`、`/tellraw` | 不改存档，但会打断所有在线玩家 |
| C3 服务器命令 | `/save-all`、`/whitelist add`、`/op`、`/deop`、`/ban`、`/kick`、`/stop`、`/restart` | 改服务器状态或**写存档** |
| C4 启动器侧动作 | 导出诊断包、重启实例、跑备份任务、切镜像 | 动文件系统 / 改运行中的实例 |
| C5 外部动作 | webhook、mclo.gs 上传 | 会把日志外传（含 IP、UUID、种子、聊天） |

### 三个具体风险画面

- **`/save-all` 撞上崩服**：日志出现 `Exception in server tick loop` 时触发自动保存，把半损坏的世界写盘。这是 C3 里最贴合你那句担忧的一条。
- **`/op` 撞上场景 B**：玩家聊天文字诱导，若 `/op` 在允许列表里，一条文字就换来管理权限。
- **`/stop` 撞上刷屏**：模组高频触发，服务器被反复关停。C3 里的幂等性最差。
- **C5 撞上隐私**：013 轮 Q-C15 定过「脱敏处理（当然用户可以手动不脱敏）」。如果自动动作能直接外传日志，脱敏开关就必须是发送前的硬闸，不能只是设置里一个勾。

### 可选口径

| 编号 | 口径 | 说明 |
| --- | --- | --- |
| Q2-A | 白名单：只允许 C1 只读，其余一律拒绝并显示可见提示 | 最保守；F028-03 会退化成「日志关键词提醒器」，自动命令名不副实 |
| Q2-B | 黑名单之外全部：沿用 013 的「黑名单」，把 `/op /deop /ban /stop /restart /whitelist` 列为**不可禁用**的核心黑名单，其余允许 | 最贴合你已有口径；但输入是日志文字，黑名单必须硬编码进核心，插件和用户都不能关 |
| Q2-C | 动作分级 + 用户逐条勾选：C1–C5 五类，默认只开 C1，每类带一句风险说明，用户自己按需打开 | 最可控；设置页多一组开关，和「设置九分组」不冲突 |
| Q2-D | Q2-B + Q2-C：黑名单做不可禁用的底，五类开关做用户可见面 | 两层都留痕，但实现最重 |

**我倾向 Q2-D 的简化版（Q2-B 打底 + C1 默认开）**，因为 013 你已经选过黑名单，这里不该另起一套。同样没写进功能 md。
